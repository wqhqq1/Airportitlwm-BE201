# AirportItlwm 1.2.13：跟随接收设备自己的时间表

默认行为与之前相同：ROC 和第二信道开关默认关闭，只在实验工具或 `开启跨信道隔空投送.command` 里打开（只在内存里，重启后失效）。蓝牙驱动没有改动。

## 1.2.12 的实验结果（2026-11-14 08:14，`roc-20261114-081416.txt`）

| 阶段 | 速度 | 实际对端 |
|---|---|---|
| 默认 | 0.03 MB/s（传了 3.2 MB 后卡住） | iPad Pro（0A:91:…） |
| 只留 1 个时隙 | 0.00 MB/s | iPad Pro |
| TID 3 队列 | 1.43 MB/s，149 时间占比 72% | iPhone（5A:A4:…，08:18 起） |
| TID 3 + A-MSDU | 0.01 MB/s | iPhone |

## 原因

1. **系统日志：**
   - 08:16:14 sharingd 的 QUIC 连接以"No route to host"失败，AirDrop 报"FileTransferFailed"。
   - 之前 AWDL 栈记录了"In AW: Tx:0 Rx:0"，随后进入 Idle，再进入 Low Power。时间表缩回到只有 3 个时隙在 149，传输越来越慢，直到断开。
2. **成功和失败的分界是对端设备：**
   - 成功的几次（22:50、08:02、08:18）都是发给 iPhone；
   - 卡住的两次（07:55、08:14）都是发给 iPad Pro。
3. **驱动的问题：** 驱动只记一份"参考设备"的时间表，同一个 AWDL 集群里，谁的同步帧最后到就用谁的。
   - 旁边闲着的 iPhone 一直发空闲时间表（149 149 149 0 0 0 0 0 6 149 149 0 …），不断覆盖 iPad 的时间表；
   - 结果 Mac 按 iPhone 的空闲时隙去 149，没有跟上 iPad 展开后的时隙；
   - 证据：卡住时每个 ROC 只发出约 5 帧，收到 iPad 的帧也很少（317，正常时约 14000–18000）。
4. **A-MSDU：** 换成 TID 3 队列后，发出 166 个、完成 16 个，传输随即停住，卡住保护按预期停用了它。所以 AUX 上的 A-MSDU 不管用哪个队列都不可用，这条路关闭，下一步按路线图做 80 MHz ROC。

## 改动

1. **单独记录接收设备的时间表：** 驱动另外记一份"数据正在发往的那台设备"自己的时间表（来自它的同步帧和 MIF），不再被别的设备覆盖。
2. **并集优先用接收设备的时间表：** 最近 2 秒内收到过它的时间表，就用它；否则仍用参考设备的。
3. **实验工具：**
   - 每段新增"接收设备时间表"、跟随了多少个时隙、收到多少次；
   - R2 改为：默认 60 秒、继续 45 秒、只留 1 个时隙给路由器 45 秒；
   - 去掉 A-MSDU 段。

## 下次怎么看

- **最好分别发给 iPad 和 iPhone 各测一次。**
- **发给 iPad 时：**
  - "接收设备时间表"应该是展开的，大部分时隙是 149；
  - "跟随"的时隙数应远大于 0；
  - 速度应接近发给 iPhone 时的 2 MB/s，而且不应再出现"No route to host"。
- **只留 1 个时隙：** 看 149 时间占比和路由器的丢包。
