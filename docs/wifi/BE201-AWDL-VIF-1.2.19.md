# AirportItlwm 1.2.19：手机传电脑（稀疏对端等时隙）

包含 1.2.18 的接收时间戳修复（1.2.18 写入后还没开过机）。跨信道隔空投送仍是开机默认启用（`be201_awdl_xchan=0` 关闭）。蓝牙驱动没有改动。

## 手机传电脑为什么失败（2026-11-14 12:57 和 12:58，运行的是 1.2.17，路由器在 60 信道）

1. **12:57:04** Mac 开始接收：建立 AirDrop 服务（TCP 8770 端口），并在 AWDL 上宣布 `_airdrop` 和 `_asquic`。
2. **12:57:05.97** iPhone 连了上来，但 TLS 握手用了 **2.69 秒**（同信道时约 0.1 秒）。
   - 12:57:08.68 Mac 才收到 DISCOVER 请求；
   - Mac 验证对方身份用了 2 秒；
   - iPhone 在连上约 4 秒时重置了连接，Mac 的回复（12:57:10.79）已经来不及。
3. **12:57:10** iPhone 重连。这次 TLS 也用了约 3.2 秒，DISCOVER 在 12:57:14 完成。
4. **之后 iPhone 一直没有发来 ASK**（真正传文件的请求）。12:58:19 第二次尝试时，Mac 一个连接都没有收到。

**原因：**
- 接收时，iPhone 处于空闲时间表 `[149 0 149 0 0 0 0 0 6 0 149 ...]`，16 个时隙里只有 3 个在 149。
- Mac 的 ROC 覆盖了自己 Data 模式的 12 个时隙，加上 iPhone 的 3 个；暂存的帧在任何一个 ROC 里都会发出。
- 所以 Mac 的回复大多是在 iPhone 不在 149 时发的：要么失败，要么等到下一轮，往返时间被拉到几秒。
- 我们发给 iPhone 或 iPad 时，对方会把时间表展开到 15 个时隙，所以以前没出现这个问题。

## 改动

1. **稀疏对端等时隙：**
   - 只看最近 5 秒内 Mac 发过数据的对端。如果它们在 149 的时隙都少于 8 个，发给它们的单播帧只在"其中有对端在 149"的时隙里放出。
   - 时隙换算和 ROC 覆盖用的是同一套。
   - 附近其他没在通信的设备（例如旁边的 iPad）不参与判断。
   - 时间表展开的对端（正在从 Mac 收文件的手机或 iPad）不受影响。
   - 每个时隙重新计算；超过两个时隙没有更新就自动失效，帧不会被卡住。
   - 实验开关 0x40000 可以关闭它；ROC 开关的取值上限从 0x40000 提到 0x80000。
   - 新计数 `ItlwmAwdlRocGateTicks` 和 `ItlwmAwdlRocGateWaits`，实验工具会打印"稀疏对端等时隙"。
2. **1.2.18 的接收时间戳**（QUIC 量往返时间用），这次一起生效。

## 测试

- 25 个离线测试套件全部通过。新增的单元测试覆盖：
  - 只有单播帧、对端稀疏、当前不在对端时隙、状态新鲜时才等；
  - 只计入最近有数据的对端；附近没在通信的设备和数据过旧的对端都不算。
- 编译没有警告。和 1.2.18 相比没有新增导入符号。

## 下次怎么看

1. **手机传电脑：** 重启后直接从 iPhone 发一个文件到 Mac，不用开实验工具，看能否开始并传完。
2. **电脑传 iPad：** 运行实验工具，看速度和"接收时间戳 已设 / 未设"。
3. **"稀疏对端等时隙"：** 接收时应该有数字；发给展开的手机或 iPad 时应该接近 0。
