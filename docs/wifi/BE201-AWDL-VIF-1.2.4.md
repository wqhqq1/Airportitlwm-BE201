# AirportItlwm 1.2.4：在 149 时隙开始前提前上频道，赶上手机的可用窗口

默认行为与之前相同：ROC 和第二信道开关默认关闭，只在实验工具或 `开启跨信道隔空投送.command` 里打开（只在内存里，重启后失效）。蓝牙驱动没有改动。

## 1.2.3 的实验结果（2026-11-13 19:20，`roc-20261113-192034.txt`）

路由器在 2.4 GHz 的 5 信道。系统和手机的时间表全程都是空闲状态（149 只有单个时隙）。

| R2 阶段 | AUX 单播数据 成功/失败 | ROC 结束后才失败 | 完成时手机时间表未知 | ROC 期间收到手机的帧 |
|---|---|---|---|---|
| 默认 60 秒 | 0 / 145 | 141 | 132 | 25 |
| 默认（继续）45 秒 | 0 / 104 | 102 | 84 | 39 |
| 按手机定时 45 秒 | 0 / 278 | 256 | 196 | 129 |

- **队列没有卡住：** 定时器检查了几千次，默认两段重新唤醒 0 次。1.2.3 的推断（写指针被错过）不成立。
- **手机多半不在：** 大多数失败帧完成时，2 秒内都没收到过手机的同步帧，ROC 期间也几乎收不到手机的帧。成功的 17:23 那次能收到 2468 个。
- **路由器正常：** 丢包 0%，没有漏信标暂停。

**判断：**
- 空闲时，AWDL 设备只保证在每个时隙开头的可用窗口（AW，约 16 TU）里在频道上。
- 我们的 ROC 在本机时隙开始后平均约 5.5 ms 才上 149，暂存的帧又等 2 ms 才放，正好错过了大半个窗口。
- 窗口一过，手机就回到路由器信道或者休眠了。传输在跑时手机整个时隙都在，所以同样的路径能通。

## 改动

1. **提前申请 ROC：** 当前时隙不在 149、而下一个时隙开始一段 149 时，用定时器在边界前 **12 ms** 申请 ROC，一直覆盖到这段 149 结束（`iwx_awdl_roc_pre`）。这样电脑在手机可用窗口一开始就已经在 149 上。
   - 规则和时隙路径一样：没有挂起的 ROC、和上次结束间隔 10 ms、漏信标时暂停、受 DTIM 上限约束。
2. **放帧时机：**
   - 提前上来的 ROC，暂存的帧在时隙边界后 **0.5 ms** 放出，集中在窗口里发。
   - 迟到的 ROC（上频道时边界已过）立刻放。
   - 其他 ROC 仍在开始后 2 ms 放。
3. **开关 0x1000** 可关闭提前申请，用来对照；开关接受小于 0x2000 的值。
4. **新计数：**
   - `RocPreArms` / `RocPreAdds` / `RocPreSkips`：定时器启动、真正申请、跳过的次数；
   - `RocPreOnTime` / `RocPreLate`：提前就位还是迟到。
5. **`roc_test.py`：**
   - R2 默认（提前上 149）60 秒，请重新发一次文件；
   - 同样设置继续 45 秒；
   - 不提前（0x1000）45 秒，作对照；
   - 每段会打印提前申请次数、就位/迟到次数，以及 ROC 期间收到手机的帧数。

## 下次怎么看

- **"提前上 149 申请 X/Y 次，就位 N 次 迟到 M 次"：** 就位应占多数。
- **"ROC 期间收到手机的帧"：** 提前之后应明显增多，说明赶上了手机的窗口。
- **"AUX 单播数据 成功/失败"：** 空闲时不再是 0，并且明显好于"不提前"那段。
- **如果手机的帧多了、单播仍然全失败：** 说明手机在窗口里但不接受我们的单播。下一步要查 AUX 发出的帧本身（地址、速率、保护方式），到那时考虑请 Fable 5.2 一起分析。
